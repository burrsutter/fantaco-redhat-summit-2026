Session Broker Architecture

Where does the user-to-route assignment logic live?

A

Node.js Broker Service + SQLite

A small Node.js/Express service on the EC2 instance that:

  • Serves as the HAProxy default backend for unmapped requests
  • Checks cookie → looks up assignment in SQLite
  • If new user → picks an available route, sets cookie, redirects to claw-NNN.yougetaclaw.com
  • If returning user → redirects to their assigned route
  • Serves the read-only status board UI
  • Reads the route pool from the same routes.csv

Pros

  • Full control, easy to extend
  • SQLite = zero infrastructure, survives restarts
  • Status board is just another Express route
  • Can health-check backends before assigning

Cons

  • Another process to manage on EC2
  • Node.js runtime dependency
B

HAProxy Lua + Stick Tables

Pure HAProxy solution using Lua scripting and stick tables:

  • Lua script runs inside HAProxy on each request
  • Stick table maps cookie values to backend routes
  • New user → Lua picks next available route, sets cookie
  • Returning user → stick table lookup, forward directly
  • Status board would need a separate lightweight server

Pros

  • No separate process — everything in HAProxy
  • Very fast — in-process routing

Cons

  • Stick tables lost on restart (no persistence)
  • Lua in HAProxy is limited (no SQLite, awkward I/O)
  • Still need a separate service for the status board
  • Harder to debug and maintain
  • "Admin release" is awkward via stick table API
C

Go Binary Broker + SQLite

Same architecture as Option A but written in Go:

  • Single static binary — no runtime dependencies
  • SQLite via go-sqlite3 or modernc.org/sqlite (pure Go)
  • Same role: HAProxy default backend, cookie assignment, status board

Pros

  • Single binary, no runtime dependencies
  • Lower memory footprint
  • Easy cross-compile for EC2 (linux/amd64)

Cons

  • More boilerplate for simple web UI
  • Slightly slower iteration during development
